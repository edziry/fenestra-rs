# WU-0017 typed application API and component authoring

Status: implemented; [verification](../verification/WU-0017-typed-application-api.md) records evidence and limits
Baseline: `a2d435d`
Branch: `feat/typed-application-api`

## Problem and governing scope

The [completion goal](../project-completion-goal.md) requires applications to
use named components and typed styles without handwritten schema IDs. The
format-2 panel still needs 84 lines, internal IR imports and inspector-specific
property/region conventions. The public `fenestra-ui` crate has no API.

This increment reuses the runtime, typed invalidation, spatial IR, CPU raster
and native shell governed by the [initial implementation plan](../initial-implementation-plan.md).
It introduces an application API and additive authoring format. It does not
replace the renderer or silently expand the registered format-1/2 contracts.

## Application contract

`View::new(name, root)` owns a tree of named `Element::row`, `Element::column`
and `Element::rect` values. `Style` supplies typed integer pixel dimensions,
padding, gap, RGBA8 background and input policy. Fluent constructors allow
ordinary Rust component functions to return and compose elements.

Names are globally unique ASCII identifiers in one view. Internal schema,
property and template IDs are allocated by the facade. Width, height,
background, input, padding and gap lower to typed runtime properties with
appropriate invalidation. Changing size updates placement, paint and hit
geometry together; failed updates publish no partial state.

Default style is 64 by 64 pixels, zero padding/gap, transparent background and
disabled input. Dimensions are fixed pixel sizes in this first API; no flex,
percent, text sizing or responsive fill behavior is implied. Rectangles cannot
contain children or container spacing. Rows and columns compose fixed children
in source order using the existing layout implementation.

`Application::new(view, Size)` and `with_limits` create the real runtime.
Application methods expose named node lookup, style mutation, hit testing,
viewport resize and owned RGBA8 raster output. Application code owns Rust state
and event handlers. No parser is part of the target execution path.

`Limits` exposes node, depth and raster-pixel budgets. Defaults are 1,024 nodes,
64 levels and 4,194,304 pixels; these are defensive development defaults, not
measured performance promises. All internal capacities derive from checked
tree counts and the declared limits. The format-2 eight-instance and
four-level experiment profile is not reused by the facade.

## Authoring format 3

The standalone file and macro body use the same structure:

```text
format 3;
view hello {
  row cards {
    width: 240;
    height: 120;
    padding: 12;
    gap: 8;
    rect first {
      width: 56;
      height: 64;
      background: rgba8(48, 128, 192, 255);
      input: accept;
    }
  }
}
```

Property order is immaterial; duplicate properties, duplicate element names,
unknown components/properties, invalid values and missing punctuation produce
source diagnostics. The compiler emits public facade constructors. `.fen`
uses a host build helper; `ui!` emits the same expression during Rust
compilation. Existing format-1/2 outputs continue to use their frozen IR
contracts. The new format does not add embedded Rust blocks or a VM.

Format 3 accepts line comments and nested block comments; their removal
preserves physical byte offsets. Rust documentation comments are rejected.
Macro errors retain Rust token spans, while `.fen` and build-helper errors
report byte-based source locations. Generated expressions currently use the
canonical `fenestra_ui` crate path; a renamed dependency needs a crate-root
alias. This restriction remains a later hygiene improvement.

The host compiler bounds source bytes, token count, element count, nesting
depth and generated bytes. Its default profile is 256 KiB source, 65,536
tokens, 1,024 elements, 64 nested elements and 1 MiB generated Rust.

## Native boundary

The optional `fenestra-ui/native` feature provides the existing winit and
softbuffer window path behind candidate-neutral content, event, size and
raster interfaces. Backend types remain private. Default facade builds do
not activate native dependencies; IR, runtime and spatial crates remain
independent of window-system candidates.

The inspector becomes a client of this shared shell and retains its public
entry points and evidence protocol. The facade must not depend on the
inspector application or GPU experiments.

## Acceptance and validation

1. A consumer depending only on the facade at runtime builds `ui!` and
   host-compiled `.fen` views without internal imports.
2. Both sources produce the same view and observable layout, hits and pixels.
3. More than eight nodes and four nesting levels work within explicit limits.
4. Named style and size changes affect the correct node and sibling layout;
   unknown nodes, invalid values and exceeded limits preserve committed state.
5. Source diagnostics retain their locations and typed causes, and both
   frontends obey inclusive resource limits.
6. Existing V1/V2 semantics, golden outputs and native evidence remain valid.
7. Shared native hosting does not self-schedule redraws, skips zero-size
   presentation and preserves supplied content and application errors.
8. Public examples run headlessly and present on the available native host;
   Windows is cross-checked separately from any native support claim.

Use failing regression or consumer tests before each implementation slice,
then the repository formatting, Clippy, docs, dependency and full test gates.
Text, focus, IME, controls, keyed application reconstruction and flexible
layout remain explicit subsequent work toward the full completion goal.
